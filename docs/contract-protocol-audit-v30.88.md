# Contract / protocol audit — v30.88 beta

## Scope

v30.88 changes three runtime semantic surfaces:

- root memory/continuity policy — capability availability versus actual context exposure;
- `code-orchestrator` — fresh-review isolation must not become speculative integration disabling/reconfiguration;
- `reviewer` — available recall capability is not contamination, while actually exposed prior-task steering remains contamination.

No role permissions, topology edges, publication lifecycle, controller activation, implementation/debug/test/UI ownership, or memory integration configuration changes.

## Semantic boundary

The controlling distinction is:

`available capability != model-visible prior-task content != contaminating investigative steering`.

Freshness is not blocked by the first state. The second state is evaluated by content. Prior-task findings, fix history, expected weak points, investigation plans, test recipes, claimed-clean areas, or equivalent steering contaminate fresh judgment when actually model-visible. Generic capability availability and hypothetical access do not.

Persistent memory remains non-authoritative recall context. A fresh reviewer does not proactively load prior-task/session memory merely to enrich its context, and material task authority must come from authoritative user/task/project records.

## Isolation behavior

If actual contaminating content is observed, reviewer stops before substantive fresh whole-change judgment and requests a clean assignment/invocation boundary. The workflow owner prefers a clean invocation boundary and considers integration reconfiguration only when no clean boundary exists and the change is separately authorized.
