# v30.33 beta

## Purpose

Separate pre-mutation semantic gating from post-hoc instruction diagnosis so each role has one lifecycle contract.

## Changes

- Adds `semantic-checkpoint`, a read-only subagent that evaluates material candidate decisions after discovery and before an edit-capable handoff.
- `semantic-checkpoint` returns only `proceed`, `hold`, or `unverified`; it does not classify historical failures, redesign the fix, or propose prompt changes.
- `code-orchestrator` invokes the checkpoint only when a discovered candidate materially establishes or changes required behavior, acceptance, scope, ownership, invariant, fix level, or product/domain policy. Routine technical mechanics do not trigger it.
- Concrete factual findings with recoverable child-session source basis may support the checkpoint without duplicating discovery, while report-only assertions can remain `unverified` and recommendations remain derived claims.
- Post-mutation verification that can exist only after implementation is not treated as a pre-mutation semantic blocker by itself.
- `session-evaluator` remains post-hoc and diagnostic. Evidence status is independent from failure classification; `instruction-gap` now requires a demonstrated absence of an applicable reusable rule, while clear semantic-rule violations stay `instruction-violation` and ordinary operational mistakes stay `execution-error`.
- Post-hoc evaluation ignores prior evaluator diagnoses as workflow evidence and treats `semantic-checkpoint` only as gate-control evidence (for example, whether `hold` was obeyed), never as independent authority for the underlying requirement.

## Evaluation basis

The split follows a live blind replay of a real pre-mutation failure. Independent model runs showed that a narrow checkpoint could block the bad handoff, while post-hoc failure taxonomy created avoidable classification pressure. The shipped prompts therefore keep gating and instruction diagnosis separate rather than adding a mode switch to one role.
