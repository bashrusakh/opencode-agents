# v28.37 — Semantic correspondence

v28.37 does not add another bug-class rule. It refines v28.36 so the canonical review/verification question is independent of framework, subsystem, state model, or implementation technique.

## Core rule

A workflow must state the **semantic property or outcome** it needs to prove before using implementation details as evidence. An implementation fact, mechanism, or test result is not automatically equivalent to that semantic property.

The correspondence must be established from actual system behavior.

For a material correctness premise:

1. state what must be true semantically;
2. identify the concrete implementation facts and the semantic conclusion being inferred from them;
3. trace enough actual system behavior to justify that direction of inference;
4. look for an ordinary valid behavior where the same technical evidence would not justify the claimed semantic conclusion;
5. prove the reverse direction separately only when the implementation or review actually relies on it;
6. if the required inference is not established, keep the mechanism as a hypothesis and revise the contract or implementation rather than declaring success.

This is intentionally generic. It does not enumerate special handling for particular frameworks, stateful/async code, caches, concurrency, identity, UI, networking, or other classes.

## Review

`@reviewer` now evaluates material claims through that same semantic-correspondence test. Agreement between implementation, comments, tests, and caller wording is not independent proof when all of them encode the same unproven proxy.

Changed-file coverage remains distinct from semantic-proof coverage: unchanged adjacent code may be necessary to establish whether a technical proxy really represents the claimed behavior.

## Verification

`@tester` no longer uses a taxonomy of special cases. Any test result counts as production evidence only to the extent that the observed result actually justifies the production conclusion being claimed.

If the same observed result can arise from test-only conditions while the claimed production property differs, the result is test-scoped evidence rather than production proof.

## Handoffs and planning

`@code-orchestrator` and `@plan` state acceptance in semantic terms. Proposed implementation details may be passed downstream as hypotheses, but they do not become acceptance criteria until evidence establishes their correspondence to the intended outcome.

## Preserved behavior

v28.37 does not change OCR delegation/managed escalation, reviewer read-only boundaries, model agnosticism, permissions, PR lifecycle, freshness/state identity/base-drift policy, or the outcome-owned fix-boundary rule.
