# v28.32 release notes

v28.32 closes the remaining stale-state gap after v28.31. Fetching the correct authoritative ref is not enough if later agents read, execute, edit, test, or review a different worktree. The workflow now carries one explicit state identity through those stages.

## State identity chain

```text
inspect ref/SHA -> executable workspace -> mutation baseline -> verification/review -> publication
```

Static current-upstream inspection may use ref-aware Git reads without checkout. Runtime evidence for a named target requires an executing workspace proven to represent that target. A current-target fix starts from the proven intended baseline rather than a stale/unrelated checkout. Candidate review/publication keeps the existing exact-SHA rule.

## Direct commands own missing-parent freshness

When `/debug`, `/verify`, `/review`, `/code-explore`, `/audit`, or another role is invoked directly, there may be no parent orchestrator to perform the v28.31 freshness step. A directly invoked role now owns applicable current-state freshness within its capabilities. Delegated leaf roles still do not fetch routinely; they inherit the caller's authoritative target/state identity.

## Issue-derived work resolves its target explicitly

An issue/report is not permission to assume the current checkout is the affected state. New issue-derived work resolves the applicability target from issue/project metadata; when publication depends on current upstream behavior, a moved authoritative SHA is rechecked before the issue is published. Ref-aware analysis also keeps applicable project guidance/config/tests on the same state as the code claim.

## State identity survives nested delegation

The workflow owner passes authoritative `ref@SHA` plus intended execution/mutation state through nested orchestrators and specialists. A child role must either operate on that state or report a mismatch/gap instead of silently substituting local files.

## Executable evidence is tied to the workspace that ran it

Tester records executing HEAD and relevant dirty state when evidence is claimed for a named target/Candidate. A mismatched checkout may still produce useful workspace evidence, but it is not verification of the supplied target.

## Mutation baseline is explicit

Debugger, build, and UI implementation verify before editing that their worktree represents the intended baseline. Non-mutation orchestrators do not use `pull`/checkout to prepare another role's workspace. If safe preparation is unavailable or not authorized, mutation stops instead of proceeding on stale code.

## UI options command consistency

`/ui-options` now produces only materially distinct directions that genuinely exist. It no longer forces 2–3 alternatives, matching the root/UI policy.

## Unchanged

- v28.29 tester batching/cadence remains unchanged.
- v28.28 review-before-push Candidate lifecycle remains unchanged.
- v28.30 iteration reset/user-decision/output rules remain unchanged.
- v28.31 authoritative-ref freshness remains the basis for current-upstream claims.
- Agent modes/permissions and bundled skills are unchanged.
