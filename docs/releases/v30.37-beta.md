# v30.37 beta

## Purpose

Close the remaining provenance-retrieval gap when the active `code-orchestrator` parent is a continuation/resume rather than the session that originally received the user's authority.

A complete read of the current parent and its descendants can still be insufficient when the current parent starts with a continuation such as `continue`, while the adopted specification, publication approval, or other material authority lives in a retrievable predecessor session.

## Runtime change

Two diagnostic/gate roles change semantically. Root workflow policy and `code-orchestrator` lifecycle rules are unchanged.

### `semantic-checkpoint`

Before returning `unverified` for missing historical authority/evidence, the checkpoint now:

- detects when the current parent is only a continuation/resume or explicitly depends on an earlier session/decision;
- follows session metadata and explicit workflow references far enough to recover the material predecessor/ancestor source;
- reads only predecessor sessions material to the unresolved provenance;
- never treats continuation wording or an agent restatement as a substitute for the original authority.

The v30.36 complete-parent-user-history and full material-child retrieval rules remain in force.

### `session-evaluator`

The evaluator already reads the current parent and every participating descendant with full history. v30.37 makes the audited evidence graph include a bounded predecessor/ancestor provenance chain when the current parent depends on earlier authority or decisions.

This prevents a report from treating authority as unrecoverable merely because the current parent contains only a continuation message while the original source remains retrievable in a referenced predecessor session.

### Boundedness

This is not a requirement to crawl every prior session in a project. Predecessor expansion occurs only when the material authority/evidence chain points outside the current parent tree. Unrelated prior sessions remain outside the audit/gate obligation.

If the material predecessor cannot be identified or retrieved, the dependent claim remains `unverified`.

## Regression scenarios

The semantic audit covers:

1. current parent contains the original user authority -> no predecessor expansion;
2. current parent contains only `continue`, predecessor contains the adopted specification -> recover predecessor before absence claim;
3. child/parent says “user approved” but no primary source is retrievable -> remain `unverified`;
4. explicit earlier session ID carries material approval -> follow it;
5. unrelated older sibling/project session -> do not read merely for completeness;
6. session-evaluator reads all descendants but original authority is in a predecessor -> predecessor recovery required;
7. predecessor unavailable -> only dependent conclusions are `unverified`;
8. current v30.35 fresh-child and v30.36 bounded/full-history rules remain unchanged.

## Non-changes

- No new agent, skill, command, or tool.
- No change to checkpoint trigger/verdict semantics.
- No change to subagent fresh-session policy.
- No change to `code-orchestrator.md`.
- No provider/model-specific routing.
