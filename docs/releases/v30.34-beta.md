# v30.34 beta

## Purpose

Close the lifecycle gap between a `semantic-checkpoint` verdict and the next `code-orchestrator` action while preserving manager ownership and implementation-role autonomy.

## Runtime change

Only `agents/code-orchestrator.md` changes runtime behavior in this release (besides the root version marker).

- `proceed` authorizes the checked candidate only within the semantic boundary the checkpoint evaluated.
- A mechanism named in the candidate or checkpoint report does not become acceptance merely because the checkpoint returned `proceed`; non-required mechanisms stay hypotheses/options for the implementation specialist.
- `hold` / `unverified` block mutation. The orchestrator carries the stated material blockers forward as diagnostic evidence and resolves them through read-only evidence or existing/user authority as appropriate.
- A blocked candidate is re-checked only after new authority/evidence or a materially revised candidate addresses the blockers. Re-running an unchanged candidate merely to obtain a different verdict is forbidden.
- Later evidence that materially changes a previously checked boundary requires a new checkpoint before implementation of that changed boundary.
- `proceed` does not waive post-mutation verification or review.

`semantic-checkpoint.md`, `session-evaluator.md`, and the root claim-authority policy are otherwise unchanged: the checkpoint still does not choose replacement implementations or create task authority, and the post-hoc evaluator already treats checkpoint invocation/verdict only as gate-control evidence.

## Design basis

The change follows a live intermediate checkpoint in which the gate correctly returned `proceed` while explicitly distinguishing the required outcome from one optional synchronous-callback mechanism. The workflow owner therefore needs to preserve the checked semantic bounds without turning that mechanism into a requirement.

The design also follows current vendor guidance used by this pack:

- OpenAI recommends manager-owned orchestration when a specialist is a bounded capability, and recommends adding specialists only when capability/policy isolation, prompt clarity, or trace legibility materially improve.
- OpenAI recommends lean, contextual standing instructions rather than accumulating broad verification rituals.
- Anthropic recommends explicit prompt chaining when an intermediate result must be inspected or branched on, while warning against unnecessary subagent/reverification loops.

These points support one narrow lifecycle rule in `code-orchestrator` rather than duplicating semantic policy into root or adding another evaluator stage.
