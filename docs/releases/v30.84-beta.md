# v30.84 beta — policy-boundary trajectory synthesis

## Purpose

v30.84 beta tightens the v30.83 longitudinal control contract around a failure class observed in a long PR-correction workflow: successive local fixes can expose materially different counterexamples to the same classifier/normalizer/policy boundary, while each individual residual is labeled `report-only`, `pre-existing`, or locally `out-of-scope`. Those labels describe local severity/provenance; they do not erase the counterexample's relevance to the quality of the shared abstraction.

The release does **not** add a helper/refactor rule and does not make every residual note blocking. It requires the workflow owner to preserve semantically convergent counterevidence and request bounded abstraction/owner reassessment before another representative-specific mutation or a readiness/publication transition that would treat the affected policy boundary as sufficiently closed.

## Runtime semantic change

Runtime semantic edits are limited to:

- `agents/code-orchestrator.md` — adds the cumulative same-policy counterexample trigger and makes `reassess` handoffs owner/representation/invariant-centered rather than file-shaped;
- `agents/trajectory-auditor.md` — makes local severity/provenance orthogonal to trajectory relevance and evaluates semantically convergent policy counterexamples without selecting the replacement design.

No runtime semantic change is made to root authority/evidence policy, `debugger`, `reviewer`, `build`, `tester`, `semantic-checkpoint`, `session-evaluator`, UI roles, or skills.

## Counterexample semantics

A `report-only`, `pre-existing`, or leaf `out-of-scope` finding remains locally scoped as reported. It enters trajectory reasoning only when it materially falsifies or weakens the **same** classifier, normalizer, policy, semantic boundary, or still-unproven assumption as the active correction chain.

This can justify `reassess` even when no single residual would block the current delta. Conversely, several unrelated low/pre-existing notes with different owners/invariants are an explicit counterexample and must not force reassessment.

## Reassessment boundary

`reassess` still does not choose a helper, refactor, architecture, or mechanism. The next bounded read-only analysis is framed around the unresolved semantic owner/representation/invariant or strategy question. Existing files, functions, call sites, and the current patch shape are evidence about the implementation that exists; they are not a preselected solution boundary unless stronger authority establishes that boundary.

## Readiness/publication boundary

The trigger applies not only before another mutation but also before a readiness/publication transition that would represent the affected semantic policy boundary as sufficiently closed. A locally non-blocking residual can therefore remain non-blocking for its delta while still requiring trajectory reassessment before a broader readiness claim.

## Regression boundary

ST-95 and ST-96 extend the trajectory suite:

- ST-95 — same-policy residual/pre-existing counterexamples require abstraction reassessment without preselecting a helper/refactor;
- ST-96 — unrelated low/pre-existing notes remain a valid anti-overreach counterexample.

These specifications and static/mutation guards are prerequisites only; fresh isolated model replay is a separate evidence class and is not claimed unless actually run.
