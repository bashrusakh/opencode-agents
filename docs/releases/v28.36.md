# v28.36

v28.36 closes a semantic-review gap: one unproven implementation assumption must not become "validated" merely because the orchestrator assignment, implementation, comments, tests, and reviewer all repeat it.

## Contract provenance and premise validation

The pack now distinguishes authoritative outcome/invariant evidence from implementation hypotheses. User/project requirements establish intended outcomes/invariants. Existing production behavior establishes current semantics and preserved behavior only where the task is not intentionally changing it. Caller-proposed mechanisms, comments/docs newly introduced by the same change, new tests, and the implementation's own description remain evidence to inspect, but they do not independently prove the premise they encode.

For materially correctness-critical guards, state transitions, identity/equality checks, ordering/ownership rules, cache keys, retries, and similar decisions, review must:

- state the semantic proposition the code relies on;
- trace relevant operands into their production producers/owners and affected consumers, reading unchanged adjacent code when necessary;
- prove representation-to-semantic mappings instead of assuming them;
- reason through an ordinary valid production transition/state that could falsify the premise; code tracing is sufficient when the behavior is statically decidable;
- report an unresolved hypothesis/gap rather than PASS when the premise cannot be established.

Changed-file coverage is therefore not equivalent to semantic-proof coverage.

## Verification fidelity

Passing tests prove the behavior of their harness. For lifecycle/state/identity/order/ownership/timing-sensitive claims, `@tester` now checks whether fixtures/mocks preserve the production property that governs the assertion. If the harness stabilizes or otherwise changes that property, the result is scoped to the harness and the production claim remains unverified.

## Delegation discipline

`@code-orchestrator` and `@plan` must keep authoritative outcomes/invariants distinct from proposed mechanisms. A speculative design choice must not be promoted into an acceptance criterion simply to make a downstream assignment deterministic.

The v28.35 delegate-first OCR review flow, v28.34 outcome-owned fix boundary, and v28.31-v28.33 state/freshness/base-drift rules remain unchanged.
