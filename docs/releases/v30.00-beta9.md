# v30.00-beta9 — root/role semantic deduplication and provenance consolidation

v30.00-beta9 applies the package ownership rules to the remaining high-overlap root and agent sections. The goal is not shorter text by itself: every removed sentence must either remain in its canonical owner or be proven redundant.

## Canonical root ownership

### Source/Startup boundaries

`Source of truth` now states what evidence is authoritative and delegates current-repository freshness mechanics to §8.1. Startup now defines only Startup ordering/format; repository freshness belongs to §8.1 and implementation scope/file-creation discipline belongs to §7.1. This removes duplicated mechanics from unrelated root sections without weakening them.

### Persistent planning

Root §2.3 remains the source of truth for when durable planning is required, the canonical `plans/<plan>/` state layout, resume behavior, authorization, and the compact `Blueprint → Gate → Execute → Digest` lifecycle. `agents/plan.md` applies that contract instead of copying the layout and global authority/fix-placement rules.

### Repository state and provenance

The former overlap between pre-edit §7.1 and publication §8.1 is consolidated into root §8.1, **Repository state and provenance**. It defines one common base/head/remote resolution and evidence model, then exposes two checkpoints:

- **Mutation baseline checkpoint** — establishes and verifies the intended worktree baseline before repository mutation.
- **Publication provenance checkpoint** — refreshes and proves task-only branch/effective-diff provenance before commit, push, PR mutation, or Ready transition.

Root §7.1 now contains only pre-edit implementation semantics and requires the §8.1 mutation checkpoint before the first mutation.

### Right-level fixes

Root §7.2 keeps the global fix-placement invariant but removes implementation taxonomies and repeated acceptance/regression prose. The rule remains: choose the narrowest existing ownership boundary capable of guaranteeing the established semantic outcome across materially affected paths; move outward or escalate when a local boundary cannot guarantee it, and do not create abstractions merely because code repeats.

### Owned PR lifecycle

Root §8.2 remains a separate Draft → Candidate → Ready state machine because PR state transitions are not the same concern as repository provenance. It now references canonical §8.1 provenance, §§7.2–7.3 fix/regression, and §7.4 evidence rather than re-explaining those mechanisms.

The Candidate ordering remains substantive and unchanged in intent: establish local Candidate HEAD, record/reconcile Base SHA, run final applicable local validation and whole-PR review before the final push, publish the exact reviewed candidate while Draft, verify remote identity/CI, then evaluate Ready. Repository-content work resumed after Ready returns the owned PR to Draft before the next update cycle.

## Verification ownership

Root §7.4 continues to define verification layers, invocation criteria, evidence identity/freshness, and honesty. Detailed batch selection/execution belongs to `agents/tester.md`; root no longer duplicates the tester's internal batch algorithm.

## Agent deduplication

The full root/agent audit removed repeated global semantics from:

- `agents/plan.md` — applies root persistent-plan layout, claim authority, and fix placement.
- `agents/build.md` — applies root routing, mutation baseline, right-level/regression, and verification contracts.
- `agents/debugger.md` — keeps root-cause/reproduction/fix execution while applying canonical claim-authority, fix-placement, regression, gate, and verification rules instead of restating them.
- `agents/code-orchestrator.md` — keeps orchestration-specific finding classification, escalation, PR/issue/release coordination, while referencing root state/provenance, fix placement, tester/reviewer cadence, and Candidate lifecycle.
- `agents/reviewer.md` — keeps complete review/OCR execution and independent judgment, while applying root claim-authority, fix/regression, and evidence-freshness contracts instead of restating them.
- `agents/general.md`, `agents/auditor.md`, and UI roles — remove stale or repeated routing/planning/policy prose while preserving their role-specific boundaries.

Intentional small cross-role protocols remain resident where independently invoked roles need them, including UI source-order/UUPM semantics and reviewer↔orchestrator finding classification vocabulary.

## Review skill routing correction

The root skill map now distinguishes the two OCR capabilities:

- deterministic review scope/rule preflight → `open-code-review-delegate` when compatible delegation is available;
- managed second-model OCR review → `open-code-review` only when the active reviewer selects escalation or user/project policy requires it.

This removes the stale implication that ordinary code/diff review should immediately load managed OCR.

## Audit result

The candidate was audited from the root outward rather than only against the edited sections:

1. protected invariant diff checks;
2. removed-rule → canonical-owner mapping;
3. reverse search for ownerless obligations;
4. placement check: root vs role based on when/who needs the rule;
5. activation/discovery check for every runtime surface;
6. semantic-similarity scan root↔agent, agent↔agent, and within root/roles;
7. stale-reference, role-capability, frontmatter, skill, installer, link, archive, and migration checks.

No package commands, snippets, or runtime policy docs are reintroduced. Runtime remains `AGENTS.md`, `agents/`, and `skills/` only. Three accidental vendored UUPM `__pycache__/*.pyc` files are removed as packaging-only debris; the skill's source/data/`SKILL.md` content is unchanged.

## Operational note

`code-orchestrator` and `auditor` remain primary-only by design, preserving the existing no-depth-increase tradeoff. The refactor does not broaden task/delegation permissions or silently change agent modes.
