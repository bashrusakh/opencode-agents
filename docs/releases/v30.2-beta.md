# v30.2 beta — Resource lifecycle and visual evidence

v30.2 beta is a focused lifecycle release built on v30.1 beta. It keeps the v30.1 routing, execution-topology, fallback, authorization, and role-capability model intact while closing a teardown gap: workflow-created temporary resources must not be silently abandoned after their last use.

## What changed

- Creating a temporary/disposable resource for the current workflow now creates an explicit cleanup obligation.
- Worktrees, local branches, remote refs, temp files/directories, local processes/services, generated evidence files, and hosted evidence resources are tracked as separate resource identities.
- Before completion, every known workflow-created temporary resource must be reconciled as:
  - `cleaned`;
  - `intentionally retained`;
  - `cleanup blocked`;
  - `ownership transferred`.
- Delegation no longer drops cleanup ownership. A specialist cleans its own temporary resources when safe or returns the exact leftovers/status to its parent; the workflow owner performs final reconciliation.
- Safe teardown of current-workflow-owned local disposable resources is ordinary workflow continuation when ownership is clear, the resource has no unique work/evidence, and removal stays inside scope.
- Cleanup of remote/published/shared/external resources remains subject to the applicable destructive/publication gate unless that exact teardown was already authorized. Authorization to create/publish is not automatically authorization to delete/unpublish later.

## Visual evidence

Visual evidence publication is distinct from the temporary workspace used to produce it. The pack does not treat a text/body API as a binary-upload mechanism and does not create a gist, temporary evidence branch/ref, commit, tag, or other durable hosting resource solely as an implicit fallback.

Use only a publication mechanism already available and authorized in the current environment. If none exists, preserve the local evidence and report publication as blocked. If publication succeeds, verify the destination contains or renders the intended evidence and reconcile the local screenshot, worktree, process/server, branch/ref, and any separately authorized hosting resource afterward.

A durable published artifact may be evidence. A temporary workspace used to produce it is not retained merely because the evidence came from it.

## What did not change

- No agent role, frontmatter `mode`, or runtime permission is broadened.
- No new nested-subagent path is introduced.
- Entry routing and delegation routing remain separate.
- Fallback remains explicit; semantic similarity still does not create a fallback.
- Hard/mandatory preconditions remain separate from user-authorizable gates.
- `plan` remains limited to portable canonical planning paths.
- Cleanup does not bypass destructive/publication authorization.

## Validation target

This beta should pass both static and failure-path review for:

- temporary worktree used for a screenshot is cleaned after the evidence is preserved, unless cleanup is blocked or ownership is explicitly transferred;
- worktree cleanup does not falsely mark a related branch/ref/process as cleaned;
- unique uncommitted/unpublished work prevents forced cleanup;
- remote/published cleanup is not silently authorized by the earlier creation action;
- a specialist returning early/failing does not erase its temporary-resource cleanup obligation;
- visual evidence uses only an already-available authorized publication mechanism;
- a successful text/comment update is not treated as proof that binary evidence was published;
- no gist/temporary branch/ref is created solely as an implicit visual-evidence hosting fallback;
- no duplicate role-local teardown contract competes with the canonical root lifecycle.
