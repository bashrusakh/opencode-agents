# v28.42 — Mutation mechanism contract

v28.42 adds one general implementation invariant for choosing how repository mutations are performed. It does not prescribe a command taxonomy or ban shell/scripted editing.

## Why

Mutation-capable roles already had strict scope, correctness, and verification contracts, but the root policy did not say how to choose between native edit/patch capabilities and broader text-processing or scripted mutation. That left models free to use a broad mechanism for a narrow semantic change even when a smaller, more inspectable mechanism was available.

The gap is about **mutation semantics**, not particular tools. A rule such as “never use `sed`/Python” would be wrong because deterministic mechanical or bulk transformations can legitimately be safer and clearer as scripts. A mandatory `rg → LSP → AST → patch` pipeline would likewise add ceremony and depend on tooling that may not exist.

## Contract

- Choose the narrowest reliable mutation mechanism for the intended change.
- Prefer native file edit/patch capabilities for bounded source changes when they can express the change safely.
- Scripted, bulk, or text-processing mutation remains valid when materially better suited to the operation or when native editing cannot safely express it.
- Broad textual replacement cannot substitute for understanding a semantic or structural code change.
- Before scripted/bulk mutation, constrain the target set and transformation explicitly; afterward, inspect the resulting diff.
- Tool choice never expands the authorized scope or weakens the correctness contract.

## Unchanged

- No tool blacklist or mandatory editing pipeline.
- No agent permission changes.
- No routing changes.
- Existing right-level-fix, semantic-correspondence, regression, reviewer/OCR, and publication rules are unchanged.
