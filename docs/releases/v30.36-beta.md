# v30.36 beta

## Purpose

Prevent `semantic-checkpoint` from turning a bounded or partially failed OpenChamber history read into a false provenance gap.

The motivating workflow already listed the complete 28-session directory with an explicit limit, but the checkpoint read only selected session histories and failed to recover complete parent authority after an invalid `all + limit` request. It then returned `unverified` even though the original user adoption remained retrievable in the parent session.

## Runtime change

Only `agents/semantic-checkpoint.md` changes semantically.

### Session discovery

- Start with `session.list` using an explicit large limit (normally `1000`), `all: true`, and `withStatus: true`.
- Use `parentID` relationships to identify the checkpoint parent and participating descendants rather than treating every same-directory session as part of the workflow.
- Do not infer completeness from OpenChamber's default-limited session listing.

### Primary authority coverage

Before claiming that historical user authority or adoption is absent:

- read the parent session's complete text-bearing user history with `role: user`, `all: true`;
- use no `limit`, `last`, or `lastAssistant` with that complete-history request;
- read full parent history when chronology/provenance cannot be resolved from the complete user stream plus current context.

This separates authority reconstruction from general evidence collection: the checkpoint does not need to read every unrelated child session merely to prove that the user once adopted a requirement.

### Material child evidence

Read full histories for participating child sessions whose factual evidence materially supports the candidate. Follow referenced earlier participating branches when a material claim depends on them. Unrelated sibling sessions remain outside the retrieval obligation.

### Tool-error recovery

OpenChamber intentionally rejects `all` combined with `limit`, `last`, or `lastAssistant`. If that usage error occurs, the checkpoint must retry with `all: true` and without the incompatible selectors. It may not fall back to a bounded recent read and then conclude that older authority/evidence is missing.

Large managed results materialized under `~/.local/share/opencode/tool-output/` remain readable by the checkpoint.

### Absence claims

`unverified` due to missing session provenance is valid only after the relevant retrievable branch has actually been exhausted. A stronger parent restatement such as “the user already approved this” still does not replace primary authority when provenance is material.

## Why this boundary

The correction is deliberately local to `semantic-checkpoint`:

- `session-evaluator` already has the analogous complete-tree/full-history retrieval discipline from v30.31;
- `code-orchestrator` already owns fresh checkpoint invocation and blocker resolution from v30.34-v30.35;
- the observed failure was the checkpoint's own evidence-retrieval strategy, not session continuity or candidate lifecycle.

No blanket requirement is added to read every session in a directory. Completeness is required for the **relevant authority/evidence path**, not for unrelated history.

## Non-changes

- No new agent or skill.
- No change to checkpoint trigger conditions or `proceed` / `hold` / `unverified` meanings.
- No change to the v30.35 fresh-child rule.
- No change to `code-orchestrator.md` or `session-evaluator.md`.
- No provider/model-specific routing.
