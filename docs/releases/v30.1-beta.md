# v30.1 beta — Semantic routing and authorization alignment

v30.1 beta is a focused semantic-policy alignment release built on v30.00. It does not add new agent roles or broaden runtime permissions. The change tightens how existing roles interpret routing, fallback, authorization, and execution topology.

## What changed

- Routing is split into two levels:
  - **entry routing** selects the top-level workflow owner;
  - **delegation routing** selects a bounded executor that is actually invokable from the current execution context.
- Agent frontmatter `mode` remains the canonical OpenCode execution topology. A semantic match does not imply a valid delegation edge.
- Fallback is no longer inferred from similar descriptions, shared tools, or apparent capability. A fallback exists only when policy explicitly declares it, the target is executable in the current context, and it preserves the current authority/workflow envelope.
- Approval logic now distinguishes hard/mandatory preconditions from user-authorizable gates. Successful tests/CI, reviewer recommendations, routing decisions, tool availability, and model confidence are evidence/state, not independent authorization sources.
- `build` now distinguishes bounded specialist delegation from a required top-level reroute to another primary-only workflow owner.
- `code-orchestrator` and `ui-orchestrator` fail closed when a required implementation role is unavailable unless an explicit valid fallback exists.
- `plan` writes are narrowed to `.opencode/plans/**/*.md` and `plans/**/*.md`; the developer-specific absolute plan path and broad `docs/**/*.md` write permission are removed.

## What did not change

- No new agent is added and no existing agent is renamed.
- Existing frontmatter `mode` values are unchanged.
- No subagent-depth increase is introduced.
- Orchestrators remain non-implementation roles by effect, not merely by editor-tool permissions.
- `ui-orchestrator` remains `mode: all`: when delegated, it may normalize/select bounded UI leaf stages but returns those assignments to the workflow-owning parent for dispatch rather than creating grandchildren.
- The runtime surface remains `AGENTS.md`, `agents/`, and `skills/`; the generic semantic review contract used to validate this release is not shipped as a parallel runtime policy surface.

## Why

The v30.00 contracts were already strong on role boundaries and effect-based no-bypass behavior, but some routing/fallback language still allowed a model to conflate a semantically appropriate role with an actually invokable role. The same issue appeared in fallback wording that could be read as permission to choose a "similar" role after failure.

v30.1 beta makes the execution topology explicit without moving the generic semantic model into pack-specific role names. The root policy states the OpenCode-specific mapping; role-local files keep only behavior that belongs to those roles.

## Validation target

This beta should pass both static and failure-path review for:

- primary-only role never treated as a `task` target;
- delegated `mode: all` behavior respecting local nesting rules;
- no inferred fallback after specialist failure;
- no shell/tool mechanism bypass of hard role boundaries;
- no implicit authorization from green CI/reviewer recommendation/tool availability;
- no project-local expansion of root-denied role capability;
- portable `plan` write paths with no broad product-doc mutation grant.
