# v30.83 beta — longitudinal trajectory auditing

## Purpose

v30.83 beta adds one bounded semantic role for a failure class that local handoff/review checks cannot see reliably: a long `code-orchestrator` workflow can make several technically valid local corrections while its cumulative task model drifts, acceptance erodes, or a repeated parent hypothesis becomes a stronger downstream premise.

The new `trajectory-auditor` is a read-only mid-workflow control role. It does not review code, diagnose/fix implementation, choose architecture, create product semantics, classify prompt defects, or own the workflow. It asks only whether the proposed next transition remains justified by the current user-authorized task anchor and cumulative primary-session evidence.

## Runtime semantic change

Runtime changes are limited to:

- new `agents/trajectory-auditor.md`;
- `agents/code-orchestrator.md` task-anchor retention, narrow longitudinal triggers, trajectory handoff construction, and verdict consumption;
- root topology registration for the new delegated role.

Existing semantic owners remain unchanged:

- root §2.2.1 owns authority/evidence/proposition semantics;
- `semantic-checkpoint` remains the pre-mutation candidate-local semantic gate;
- `session-evaluator` remains post-hoc forensic/compliance diagnosis for completed workflows;
- reviewer/tester/debugger/build/UI roles keep their existing local responsibilities.

## Trajectory method

The auditor reconstructs the current task anchor from actual user/session evidence, then the shortest material chain:

`evidence -> interpretation/hypothesis -> action/handoff -> scoped result -> end-to-end acceptance effect`.

It distinguishes acceptance, enabling, diagnostic, and no-material progress; checks for hypothesis laundering, decision-space narrowing, acceptance erosion, and scoped evidence being consumed as broader proof; and classifies repeated correction blockers as `independent`, `clustered`, or `unverified` without inferring that repetition alone means the architecture is wrong.

Verdicts are deliberately distinct from reviewer/checkpoint semantics:

- `continue`;
- `reanchor`;
- `reassess`;
- `checkpoint-required`;
- `unverified`.

The auditor never chooses a replacement fix/design. `checkpoint-required` routes a genuinely unsettled semantic proposition to the existing `semantic-checkpoint` owner.

## Trigger boundary

`code-orchestrator` must use trajectory audit when cumulative history, not one local finding, becomes material. The principal trigger is repeated locally successful correction epochs on the same end-to-end acceptance path followed by another material blocker that is not already demonstrably independent. It also applies before cumulative evidence materially changes root/fix/ownership/architecture framing, before a repeated parent hypothesis is promoted without discriminating evidence, and before terminal completion after relevant strategy-reset/repeated-correction history.

Anti-ritual controls explicitly preserve direct handling of isolated ordinary corrections, established staged work whose later acceptance is not yet expected, and evidence-backed independent defects with different owners. Turn count, session length, commit count, and review count are not triggers.

## Regression coverage

ST-85…ST-94 cover:

- local-success / global-nonprogress correction chains;
- longitudinal hypothesis laundering;
- terminal acceptance erosion;
- scoped-review evidence overclaim;
- clustered correction boundaries;
- independent-defect counterexample;
- staged-work counterexample;
- stale prior-auditor verdicts;
- parent trajectory packet vs primary session evidence;
- isolated-correction anti-ritual routing.

The new `code-orchestrator -> trajectory-auditor` edge has a dedicated high-risk handoff profile and synthetic negative selftest. `trajectory-auditor` has its own role-executability profile rather than inheriting generic audit semantics.

## Evidence limits

Static/contract/handoff/package checks prove structure, role executability, topology closure, and regression-harness sensitivity. The release separately records which trajectory cases were calibrated against historical session exports. No claim of fresh isolated model replay is made unless such a runtime replay was actually executed.
