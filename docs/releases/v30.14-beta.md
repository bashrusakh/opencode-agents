# v30.14 beta

Mutation-mechanism clarification built on v30.13 beta.

## Why

The previous root policy preferred native edit/patch for bounded source changes but allowed shell/script mutation when it was "materially better suited." Models could interpret convenience properties — for example line-number targeting, shorter syntax, or avoiding exact-match requirements — as sufficient reason to use `sed`, `python`, or similar tools for ordinary semantic edits. That made the intended exception too easy to self-justify.

## Changes

- Makes native edit/patch the default for bounded semantic changes to repository source, tests, configuration, and documentation when those capabilities are available and can express the change safely.
- Defines shell text processors and ad-hoc scripts as transformation mechanisms rather than alternate editors.
- States that convenience, shorter syntax, line-number targeting, exact-match avoidance, or a small number of textual replacements do not make scripted mutation preferable.
- Keeps scripted mutation available when the transformation itself is materially programmatic/mechanical across an explicitly bounded target set, when native edit/patch cannot safely express the operation within that target set, or when native edit/patch is unavailable.
- Keeps the existing pre-mutation target/transformation bound and post-mutation diff-inspection requirement for scripted/bulk changes.
- Adds concise role-local salience to the mutation-capable `build`, `debugger`, `ui-implementer`, and `devops` execution roles. Orchestrators still hand off semantic goals/boundaries rather than prescribing edit tools in each assignment.
- Keeps canonical planning/workflow artifacts and external scratch files under their existing role/path mechanics; appropriate append/serialization there does not create an alternate-editor exception for implementation content.

## Unchanged

- Routing, goal/path ownership, role topology, permissions, gates, provenance, PR readiness, skill inventory, and installers are unchanged.
- Planning-artifact writes remain governed by the `plan` role's existing narrow permissions and are not converted into source-edit work.
