# v28.29 release notes

v28.29 is a verification-cadence release. It keeps the v28.28 workflow ownership and review-before-push Candidate HEAD model, but removes a remaining source of ceremonial multi-agent work: treating `@tester` as the automatic next stage after every implementation package.

## Tester is now an independent checkpoint, not a post-fix ritual

**Before:** implementation roles already ran focused checks, but the orchestration flow could still say `implementation -> @tester` almost unconditionally. In complex work, `verify each package` could also be read as `run tester after every package`.

**Now:** implementation-capable roles return implementation-local evidence first. `@tester` is invoked when an independent pass materially adds confidence: explicit verification/reproduction, a meaningful integration/shared/stateful boundary, insufficient local evidence, or user/project policy. Package completion alone is not a trigger.

## One tester invocation covers one complete verification boundary

**Before:** `run the smallest relevant check first` was correct ordering, but it could be interpreted as permission to return after that one check and let the orchestrator invoke tester again for preserved behavior or a broader suite.

**Now:** tester derives the whole already-applicable verification set up front, runs the smallest check first, and then continues through focused changed behavior, preserved behavior, representative consumers/shared suites, and applicable lint/build/smoke checks in the same assignment where practical. It stops early only when a blocker/dependency makes the rest meaningless, unsafe, or outside scope. A single failing check does not end the batch when other independent applicable checks can still reveal useful failures.

## Work packages and verification checkpoints are separate concepts

**Before:** bounded implementation packages were useful for scope and mutation control, but wording such as `verify each package` encouraged one tester job per package.

**Now:** every package returns proportionate implementation-local evidence. Several related packages can then receive one independent tester checkpoint when they form a coherent integration boundary. Risky work may still get an earlier checkpoint when later mutation depends on that result.

## UI follows the same evidence model

**Before:** the UI flow could invoke tester whenever runnable frontend checks existed, even though `ui-implementer` had already performed suitable local checks.

**Now:** `ui-implementer` is expected to return local frontend evidence. `ui-orchestrator` invokes tester only when independent verification adds value, several UI changes meet at an integration boundary, local evidence is insufficient, or policy explicitly requires it.

## Reviewer is judgment, not a second tester

**Before:** read-only reviewer capability allowed non-destructive commands, which could lead a model to repeat broad tests even when fresh tester/implementation/CI evidence already existed.

**Now:** reviewer consumes current evidence and may run only narrow spot-checks needed to confirm/falsify a specific finding. Missing broader executable coverage is reported as a verification gap instead of recreating the tester stage.

## Auditor batches runtime verification

**Before:** broad audits could reasonably use tester, but several findings could become several independent tester invocations.

**Now:** auditor groups related executable questions by subsystem/invariant and sends one bounded tester assignment for that meaningful verification boundary. Existing fresh evidence is reused when sufficient; the auditor itself may use narrow finding-specific spot-checks but does not recreate or repeat broad tester/CI coverage.

## Discovery is no longer a ceremonial pre-debug stage

**Before:** the default bugfix flow could suggest `@explore` whenever the relevant code path was not already identified. In practice most bugs begin without an exact file, while `@debugger` already traces the responsible path as part of root-cause work.

**Now:** separate `@explore` is reserved for materially broad/ambiguous/cross-cutting discovery where a repository map is needed to bound mutation safely, or for an explicit discovery deliverable. A normal bounded debugger may locate the exact files itself. The same rule applies to UI discovery.

## Functional UI verification precedes final accessibility review

**Before:** the default UI sequence listed accessibility review before tester verification. A later functional failure could require another implementation edit and immediately stale the accessibility verdict.

**Now:** when both are post-implementation checks, functional/integration verification runs first and `@a11y-reviewer` examines the resulting stable UI state. Accessibility analysis may still run earlier when it is intentionally needed to choose the design/implementation direction.

## UI options, plan, and audit modes are no longer conflated

**Before:** the root UI routing grouped options, plan, and audit-only requests together and could force a `2-3 options` result even when the user asked for a single plan/audit or only one sensible direction existed. This conflicted with the UI orchestrator's own rule not to manufacture cosmetic alternatives.

**Now:** options-only returns materially distinct choices only when they genuinely exist; plan-only returns one implementable plan; audit-only returns findings/recommendations. None of these modes silently turns into implementation.

## UI PR readiness cannot skip the final reviewer

**Before:** the root owned-PR Ready gate required a final whole-change reviewer, but the UI orchestrator's stage list did not name that handoff explicitly. A direct top-level UI workflow could therefore under-emphasize the final review stage even though the root policy required it.

**Now:** UI orchestration explicitly applies the root reviewer cadence. For an owned PR Candidate, functional/integration and applicable accessibility evidence settle on the stable UI state, then the mandatory whole-change reviewer runs before the exact Candidate SHA is pushed.

## Full role-cadence audit

The v28.29 pass also checked every bundled role for the same class of sequencing error.

- **`debugger` / `build`** — keep implementation-local checks inside the mutation stage; they do not force a tester invocation merely because implementation finished. `debugger` also reuses fresh caller/tester/CI reproduction evidence instead of mechanically rerunning the same failing command before every fix.
- **`reviewer`** — explicit cadence is now defined. It is mandatory for explicit review deliverables and final owned-PR Candidate readiness; otherwise it runs only when independent judgment materially helps at a stable high-risk boundary. It consumes fresh verification instead of repeating broad tests.
- **`ui-orchestrator` / `ui-implementer`** — local UI evidence comes from implementation; tester is conditional and batched at a meaningful UI integration boundary. `a11y-reviewer` is likewise conditional: use it for materially accessibility-sensitive semantic/interaction changes or explicit policy, not merely because a UI file changed.
- **`auditor`** — tester and reviewer questions are grouped by subsystem/invariant rather than dispatched per finding.
- **`devops`** — retains direct verification of the operational target it changed; this is part of the DevOps stage and does not require a generic tester handoff.
- **`plan` / `ui-planner`** — plans distinguish implementation packages from independent verification checkpoints instead of prescribing tester after each package.
- **`explore` / `general` / `ui-auditor`** — no further sequencing defect requiring a behavior change was found; their read-only/specialist boundaries remain appropriate. `a11y-reviewer` now also distinguishes an explicitly requested pre-implementation advisory pass from the final verdict on a stable implemented UI state, matching the UI-orchestrator ordering contract.

This audit adds a general **stage economy** rule: reuse fresh evidence and re-invoke a specialist only for a changed/stale target, incomplete/blocked coverage, a newly material boundary, or genuinely independent evidence/judgment. Commit/package count alone is not a trigger.

## What did not change

- `code-orchestrator` still owns scope, stage order, escalation, mutation/publication sequencing, and final claims.
- Specialists still own technical execution inside their delegated boundary.
- v28.28 review-before-push PR ordering remains: local Candidate HEAD -> applicable local validation -> whole-PR reviewer -> push exact reviewed SHA -> remote identity/CI -> Ready.
- OCR remains reviewer-selected unless explicitly required.
- Agent modes/permissions and bundled UUPM content are unchanged.
