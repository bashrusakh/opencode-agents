# v30.82 beta — debugger falsification-loop hardening

## Purpose

v30.82 beta fixes one bounded role-executability weakness exposed by recent correction loops: `debugger` already owned root-cause diagnosis, right-level fixes, evidence fidelity, and hypothesis reset, but its role-local method did not operationalize the same cross-class falsification discipline already present in `build`. A weaker conforming debugger could therefore accept an explicit but contradictory correction premise, validate a mechanism only in a convenient local environment, or treat several correlated self-authored checks as closure.

The motivating failure class is generic: a confirmed bug enters a correction role with an existing invariant and some evidence, but the proposed diagnosis/fix remains a hypothesis. The debugger must attempt to falsify that hypothesis against materially different representatives of the already-established behavior before returning a fix.

## Runtime semantic change

Only `agents/debugger.md` changes semantically.

For non-trivial bugs, debugger now makes the relevant portion of root §7.3's case-to-verification map concrete before choosing a fix. It identifies only materially relevant classes already established by the task/repository/root contract — input, state/transition, representation, lifecycle, boundary/environment, or consumer — and chooses at least one semantically different representative capable of falsifying the current root-cause/fix hypothesis for each relevant class. The rule is proportional: it neither invents unsupported classes nor demands an arbitrary cross-product.

When correctness depends on an external grammar/API/tool/runtime or target environment, those material conditions must survive into the evidence. A convenient local surrogate cannot silently establish a target-specific proposition.

The role also makes assignment contradiction handling explicit. A caller's factual premise, fixture, mechanism/constraint, or remediation does not become correct merely because it is written as an instruction. If it conflicts with stronger behavior/evidence or a discriminating representative, debugger first determines whether it is genuinely an established implementation constraint. Non-authoritative detail resets the diagnosis/fix hypothesis; genuinely authoritative contradiction stops/escalates before mutation.

Before return, debugger actively falsifies the final mechanism against the same case map. Probes come from the governing behavior and owning abstraction, not from the patch shape, and multiple self-authored tests sharing one implementation assumption do not establish closure. Uncheckable established classes remain explicit evidence gaps.

## Why this is role-local rather than root duplication

Root §2.2.1 and §§7.2–7.3 remain the canonical semantic owners for authority/evidence, right-level fixes, preserved behavior, and case-to-verification mapping. v30.82 does not restate those policies as a second owner. It adds debugger-specific execution procedure at the decision points where that role selects and validates a correction hypothesis — analogous to the already-established build self-falsification loop.

No runtime wording changes are made to `build`, `reviewer`, or `code-orchestrator`: the observed misses there are covered by existing ownership/authority/evidence contracts and are retained as eval regressions rather than prompt accretion.

## Regression coverage

- ST-80: an explicit lower-authority correction premise that contradicts preserved behavior must cause debugger reset/escalation, not literal implementation.
- ST-81: a target-environment-dependent claim cannot be proven solely by a semantically different local tool/runtime version.
- ST-82: a successful non-reproducing diagnostic probe cannot by itself confirm the hypothesized root cause.
- ST-83: reviewer cannot use correlated implementation/self-test assumptions as sufficient proof of an external grammar/protocol claim.
- ST-84: a generic external-provider failure remains causal uncertainty until discriminating provider evidence resolves it; diagnosis may proceed without prematurely assigning a patch recipe.
- Static policy regressions bind the new debugger operational loop and the five new transition cases without claiming behavioral replay.

## Evidence limits

Contract/static/handoff checks establish that the rule, topology, and regression harness remain internally consistent. Fresh isolated behavioral replay of ST-01…ST-84 remains a separate evidence class and is not claimed by this release.
