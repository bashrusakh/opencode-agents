# v28.28 release notes

v28.28 does not replace the semantic routing, specialist roles, review workflow, or safety boundaries introduced in earlier releases. It tightens areas that already existed but were still ambiguous in longer multi-agent workflows — especially complex bug fixes and PR follow-up.

## Multi-agent workflow ownership is now explicit

**Before:** roles were separated, but a delegated specialist could still have too much freedom to interpret what should happen after its assigned task — for example whether to expand scope, start another stage, involve another agent, or negotiate a new gate.

**Now:** the orchestrator owns scope, stage order, new findings, escalation decisions, mutation/publication sequencing, evidence freshness, and final claims. Each specialist owns only the technical **how** inside its assigned boundary. If the task needs to grow or change direction, control returns to the orchestrator first.

This is intentionally not command-level micromanagement: a tester still chooses the relevant tests and a debugger still chooses the right implementation details inside the assignment.

## Complex bugs no longer default to repeated patch/review loops

**Before:** several related review findings could be processed as separate local bugs, producing a cycle of small patches and new findings even when they all came from the same underlying behavioral model.

**Now:** when findings share a state-machine, lifecycle, protocol, concurrency, persistence, ownership, retry, migration, or similar invariant, the workflow stops patching symptoms. It establishes the shared model first, then splits the correction into bounded implementation packages and verifies them against that same model.

File count or diff size alone does not trigger escalation.

## Reviewer behavior is more complete and less comment-driven

**Before:** review existed, but the policy did not strongly require the reviewer to connect multiple manifestations of the same root invariant. That made one-comment/one-patch behavior too easy.

**Now:** the reviewer inspects meaningful sibling cases inside the affected invariant, groups related manifestations into one finding, and distinguishes current regressions from design/invariant gaps, verification gaps, related latent defects, and unrelated pre-existing issues.

A review finding is evidence about the behavioral model — not automatically an instruction to patch the exact commented line.

## PR follow-up has a defined Draft → Candidate → Ready lifecycle

**Before:** PR readiness and freshness rules already existed, but active development and final review were not separated strongly enough. A changing PR could be exposed to expensive final review too early or too often.

**Now:** confirmed owned PRs stay **Draft** through implementation, CI iteration, and repair batches. When the intended implementation is complete, the exact final local commit becomes the **Candidate HEAD**. Final local verification and the whole-PR reviewer pass run against that local candidate **before push**. Only after reviewer pass is that exact reviewed SHA pushed while still Draft; the workflow then verifies that the remote PR head matches it and runs required remote CI/status checks before **Ready**. Pushing the unchanged reviewed SHA does not trigger a second full review.

If repository-content work resumes after Ready, the owned PR returns to Draft before the next changed update is published.

## Final PR review means the whole PR

**Before:** commit-level and incremental reviews were useful, but policy could still leave ambiguity about whether a sequence of partial reviews was enough for final readiness.

**Now:** final owned-PR readiness requires `@reviewer` to account for the complete base-to-**local-Candidate-HEAD** change before the final candidate push. Large changes may be reviewed in explicit slices, but all changed files/effective-diff slices must be reconciled into one `Coverage: full PR` verdict.

Earlier incremental reviews remain supporting evidence; they do not replace the integrated final pass.

## Draft repair pushes are separated from the final quality gate

**Before:** a broad rule against publishing while required verification was failing/blocked could be interpreted too strongly. In the worst reading, a Draft PR with failed CI could be prevented from receiving the repair commit needed to make CI pass.

**Now:** an already-authorized in-scope repair batch may be pushed to an owned Draft PR while checks are failing/blocked, as long as the state is reported honestly and Draft publication safety is satisfied.

Failing/blocked mandatory verification still prevents **Ready, merge, release, and completion claims**.

## Nested orchestrators no longer silently become second workflow owners

**Before:** a nested coordinator such as `ui-orchestrator` could be interpreted as having implicit freedom to launch its complete child-agent chain whenever a parent delegated UI work.

**Now:** child-stage selection must be explicitly delegated. Without that authority, the nested orchestrator performs the assigned orchestration step and returns recommended next stages to the parent.

The same principle applies to delegated user interaction: a specialist returns new scope/gate/user decisions to its parent unless interaction authority was explicitly delegated.

## PR context stays visible in reports

Reports about a specific PR now include the canonical clickable PR URL. Owned-PR readiness reports also include the current Draft/Ready state and Candidate HEAD when established.

This prevents long multi-agent reports from losing the actual PR target in the surrounding detail.

## OCR remains a reviewer tool, not a universal extra gate

The final independent reviewer remains the judgment layer. OCR can strengthen a review when the reviewer considers it useful and external sharing is allowed, or when user/project policy explicitly requires OCR.

OCR is not automatically required for every Draft → Ready transition, and OCR availability alone does not determine PR readiness.

## What did not change

v28.28 is a semantic workflow-policy release, not a permissions expansion.

- agent modes/permissions were not broadened;
- provider-specific model overrides were not added;
- v28.27 semantic routing and role boundaries remain in place;
- GrayMatter remains optional external memory integration;
- bundled UI UX Pro Max content remains intentionally unchanged.
