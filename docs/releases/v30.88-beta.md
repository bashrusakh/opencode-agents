# v30.88 beta — fresh-review capability versus exposed context

## Purpose

v30.88 corrects an over-reading introduced by the v30.86/v30.87 fresh-review isolation work. A fresh reviewer does not become contaminated merely because a memory integration, connector, tool, permission, or recall capability is available. Independence is affected by task-specific judgmental/investigative content actually present in model-visible context, not by hypothetical access.

## Runtime semantic changes

### Root memory policy

- capability availability is not exposed task context;
- uncertainty that an integration might reveal prior content is not evidence that it did;
- fresh independent judgment does not proactively retrieve prior-task/session memory for context enrichment;
- integrations are not disabled or reconfigured merely to manufacture freshness; isolation changes require observed contamination, lack of a clean invocation boundary, and authorization.

### `code-orchestrator`

The workflow owner must not block a fresh review or attempt to hide/disable recall capabilities merely because they exist. It treats freshness as contaminated only when prior-task judgmental/investigative content is actually model-visible or intentionally retrieved. When actual contamination is observed, prefer a clean invocation boundary; configuration changes remain separately gated.

### `reviewer`

The reviewer now distinguishes capability from exposure. It does not treat an available memory/MCP/connector/tool as a blocker and does not proactively load prior-task memory for a fresh whole-change review. Actual prior-task steering content—whether supplied in the assignment, automatically injected, or intentionally retrieved—still contaminates fresh judgment and requires a clean assignment/invocation boundary.

## Eval / gate changes

- ST-111: available recall capability without exposed prior-task content must not block fresh review or trigger reconfiguration;
- ST-112: actually injected/retrieved prior-task investigative steering still contaminates fresh review;
- static policy guards require the capability/exposure distinction in root, orchestrator, and reviewer contracts;
- the high-risk `code-orchestrator -> reviewer` profile now protects against speculative capability-based blocking.

## Preservation

No integration is enabled, disabled, or reconfigured by this release. Memory remains optional recall context rather than task-semantic authority. Targeted re-review semantics and the v30.87 parent-derived methodology isolation rule are unchanged.

Fresh isolated behavioral replay remains a separate evidence class and is not claimed unless actually run.
