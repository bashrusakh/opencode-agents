# v28.30 release notes

v28.30 is a small workflow-hygiene release. It keeps v28.29 orchestration, verification cadence, and review-before-push semantics unchanged and adds four rules that remove avoidable iteration/user friction.

## Failed-fix spiral reset

**Before:** complexity escalation handled shared invariant/design problems, but a wrong root-cause hypothesis could still produce another similar patch after the same failure persisted.

**Now:** unchanged material failure or evidence contradicting the claimed root cause lowers confidence in that hypothesis. The orchestrator/debugger reassesses reproduction, assumptions, ownership/call path, environment, and fix level before another similar mutation. Broader invariant/design escalation is used only when the evidence actually requires it.

## Batched user decisions

**Before:** delegated specialists correctly returned user decisions to the orchestrator, but the orchestrator had no explicit rule against surfacing compatible uncertainties one by one.

**Now:** safe non-gated uncertainty is resolved from repository/tool evidence where possible. Remaining compatible decisions are batched and surfaced once when they become blocking. Approval gates are unchanged and still occur before the gated action.

## Result/action-first reporting

**Before:** output policy generally asked for a short summary first.

**Now:** the first useful information depends on state: completed work leads with the result; blocked work leads with the blocker and required action/decision; a user-executed procedure leads with its first executable step. Completed work does not invent a next action.

## Ordered human procedures

**Before:** bullets/headings were preferred, but there was no explicit distinction between executable procedures and unordered findings/status.

**Now:** numbered steps are used only when the reader must perform actions in order. Findings, options, status, and internal workflow descriptions remain bullets/sections unless ordering itself matters.

## Documentation alignment

README diagrams now explicitly show that a stable Candidate HEAD may receive an independent `@tester` checkpoint when useful/required before the mandatory final whole-change reviewer. This matches the existing v28.29 verification policy and removes the previous visual ambiguity.

## Policy placement

The four rules live in the existing contracts:

- failed-fix reset and decision batching live in the root orchestration contract, with role-specific behavior in `code-orchestrator` / `debugger`;
- result/action-first reporting and ordered human procedures live in the root output rules and `docs/output_formatting_policy.md`.

No agent modes/permissions, skill payloads, OCR policy, PR lifecycle, or verification cadence were broadened by this release.
