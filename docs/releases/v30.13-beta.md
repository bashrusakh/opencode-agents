# v30.13 beta

Repository-prerequisite readiness clarification built on v30.12 beta.

## Why

A repository may require a product/design decision or another approval outside the PR before the change is ready for maintainer review. Treating the external artifact itself (for example, an open discussion or forum topic) as the blocker is too coarse: a decision can be settled while the artifact stays open, and an artifact can be closed without establishing the required decision.

## Changes

- Adds **Repository prerequisites** to the canonical `pr-readiness` Ready-for-review gate.
- A prerequisite may be recorded through a discussion, issue, RFC, forum, mailing list, or another repository-defined process; the medium does not define the gate.
- Applicability and satisfaction are derived from authoritative repository policy, maintainer decisions, and current authoritative repository/review/status signals.
- Open/closed/linked state alone is neither proof of unresolved status nor proof of resolution.
- An owned PR stays Draft only while the required decision/approval itself remains unresolved, or while repository policy explicitly requires another unsatisfied state.
- Once the prerequisite and all other Ready conditions are satisfied, the workflow proceeds to Ready without waiting for ceremonial closure of the external artifact.
- PR metadata must not claim agreement/resolution that the authoritative record does not establish.
- Repository-prerequisite evidence is refreshed before Ready when it can change independently of Candidate HEAD; an unchanged commit does not make external decision state fresh.
- If an owned PR is already Ready when a mandatory prerequisite is discovered/becomes unresolved, readiness is stale; return to Draft when that PR-state transition is already authorized, otherwise report the state mismatch as a blocker.
- While blocked, the workflow may continue only already-authorized work that legitimately helps resolve or prepare for the prerequisite; it must not implement a disputed product/design choice merely to make progress.

## Scope

The rule is repository-agnostic. It does not special-case GitHub Discussions, labels, or OpenChamber. Project-specific labels/checks/review signals remain evidence only to the extent that the repository defines them as authoritative for readiness.

## Unchanged

- v30.12 Magic Compact/context-hygiene behavior.
- Agent routing and role capability boundaries.
- Approval/publication gates.
- Installer behavior and bundled skill inventory.
