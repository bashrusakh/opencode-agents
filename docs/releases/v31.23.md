# v31.23 candidate — decision-complete product questions

**Status:** Candidate. Static/package gates and cross-version preservation pass. Real-model behavioral replay has not been run, so this bundle makes no claim that a live model has demonstrated the new behavior.

## Summary

This release strengthens the code orchestrator's handling of material product and scope decisions. The existing rule already required questions to be self-contained; this change makes the required explanation operational and testable.

Before asking the user, the orchestrator must reconstruct relevant current project state and explain, in plain language:

- what capability or workflow is being decided, what it does, and whose need it serves;
- why each genuinely viable alternative exists and what practical outcome it produces;
- the material benefits, limitations, costs, and compatibility consequences of each option;
- which option is better supported by the established goal and evidence, and why—or precisely what remains unknown if evidence cannot support a recommendation;
- material effects on integrated behavior and pending work when they affect the decision.

The question must be compact but decision-complete. It must not rely on unexplained implementation terms, ask the user to reconstruct prior sessions/PRs, reduce the decision to a bare `A or B?`, or become a wall of technical detail.

## Evaluation

Adds three end-to-end scenarios to `evals/semantic-transition-traces.md`:

- **ST-156:** explains the capability, the purpose of both alternatives, their practical outcomes, and the reasoned recommendation;
- **ST-157:** reconstructs distributed current project state and decision provenance without asking the user to recall sessions or PRs;
- **ST-158:** preserves decision-critical meaning while omitting irrelevant implementation detail.

The existing ST-73 and ST-74 remain in force: decision requests must be self-contained, and evidence-resolvable technical uncertainty must not be promoted into a user product choice.

## Preserved boundaries

- `AGENTS.md` authority and decision-binding rules are unchanged.
- Safe factual/technical uncertainty is still resolved from evidence before asking.
- Ordinary implementation discretion remains with the owning role.
- User approval is still required only for genuinely user-owned choices.
- No new role, skill, permission, workflow stage, mandatory template, or approval gate is introduced.
