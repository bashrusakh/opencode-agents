# v30.78 beta — orchestrator workflow visibility and decision-context completeness

## Purpose

v30.78 fixes two communication failures observed in real `code-orchestrator` traces without weakening the pack's anti-narration rules:

1. a long multi-stage workflow could emit Startup and then become effectively silent while only raw tool/specialist activity remained visible until Final;
2. a specialist-raised ambiguity could be surfaced as a terse user choice even though the user had not seen the child/tool context needed to understand what was being decided.

The change is deliberately role-local where the observed failure lives. Root communication cadence and UI-orchestrator behavior are not broadened by default.

## Runtime behavior

### Workflow-state milestone synthesis

`code-orchestrator` now distinguishes semantic workflow progress from execution narration.

After a meaningful stage or batched evidence result establishes new current workflow state and determines the next materially different stage/owner, the orchestrator briefly synthesizes:

- what is now established or still unresolved;
- which stage/owner comes next and why.

It still does **not** narrate every command, tool call, specialist invocation, completed mechanical substep, or individual evidence point. A short single-stage workflow may still use the compact `Startup -> tools -> Final` shape.

### Decision-context completeness

Before asking the user to resolve a material choice, `code-orchestrator` must first distinguish:

- factual/technical uncertainty that safe read-only evidence or the owning specialist can resolve;
- role-owned implementation discretion;
- a genuinely independently choosable user/product/scope/authority decision.

Only the last category is surfaced as a user choice. When it is, the decision request must be self-contained for someone who did not see child sessions or tool output: affected behavior/surface and why it matters, material established facts, viable alternatives and their consequences/tradeoffs, an evidence-supported recommendation when one exists, then the exact proposition/options.

This extends the existing anti-bundling and decision-batching semantics; it does not create authority for new product choices.

## Methodology/source alignment

The Semantic Design Manual now records the two reusable behaviors as communication-harness semantics rather than incident-specific prompt patches.

The source-preservation audit additionally tracks current guidance from:

- OpenAI GPT-6 agentic eagerness / clarification: complete already-authorized read-only/reversible work needed to make the remaining action concrete and reviewable before asking for clarification;
- Anthropic Opus 5.5 progress updates: long agentic work benefits from short user-facing `what was found -> what comes next` visibility, with cadence explicitly tuned rather than tool-by-tool narration.

The preservation matrix is now **19/19 PASS**.

## Contract/eval changes

`code-orchestrator` receives a dedicated contract-audit profile so the two new communication capabilities do not silently become requirements for every orchestrator-like role:

- `workflow_state_visibility`;
- `decision_context`.

Both are material REVIEW-level capabilities in the contract audit: their absence blocks promotion but does not misclassify the basic orchestration loop as non-executable.

ST-71…ST-74 add adversarial/preservation scenarios for:

- milestone synthesis in long multi-stage work;
- preservation against per-tool status spam;
- self-contained decisions derived from hidden specialist context;
- preventing evidence-resolvable technical ambiguity from being promoted into a user product choice.

Fresh isolated behavioral replay of ST-01…ST-74 remains pending and is not implied by static/contract/package PASS.
