# v28.40 — Runtime-valid role routing

v28.40 aligns agent modes and delegation semantics with the routing contract already described by the pack.

## Role modes

- `build`: `primary` -> `all`. Direct use remains a focused primary implementation path; delegated use is a bounded implementation leaf and must return follow-on stages to its parent.
- `plan`: `primary` -> `all`. Direct planning remains available; delegated planning remains leaf-only because `task: deny` is unchanged.
- `ui-orchestrator`: `primary` -> `all`. As the active primary it may dispatch UI specialists. When invoked by another orchestrator it may normalize the delegated UI domain and select/prepare bounded leaf assignments, but returns those assignments to the workflow owner for dispatch.
- `debugger`: unchanged as `subagent` + `task: deny`, preserving its confirmed-failure/root-cause/fix boundary.

## One workflow owner across orchestrator boundaries

Stage-selection authority no longer implies nested dispatch authority. A delegated domain orchestrator can decide which leaf stages apply when that decision is delegated, but the workflow-owning parent remains the dispatcher. This keeps the bundle compatible with the default one-generation subagent model without increasing `subagent_depth`.

## UI routing

A focused, already-understood UI implementation now routes directly to `ui-implementer`. UI options/audit/redesign/unresolved direction or coordinated multi-stage UI work routes to `ui-orchestrator`. This avoids a ceremonial orchestrator hop for simple UI edits while preserving the specialized UI workflow when it adds value.

## Consistency cleanup

The primary-only `auditor` no longer documents a nested-dispatch path that the packaged runtime mode cannot provide. No model override, OCR policy, publication gate, or verification policy changes in this release.
