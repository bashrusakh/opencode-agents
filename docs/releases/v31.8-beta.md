# v31.8 beta — Correct-fix adequacy across the workflow

The v31.7 improvement to alternative selection was framed principally as a pre-implementation issue/TZ assessment. The actual decision is whether the **selected fix** can deliver authoritative end-to-end acceptance with preserved behavior. An initially approved technical specification or patch approach is evidence/authority for its explicit constraints, but not by itself proof of the fix's adequacy.

`code-orchestrator` now applies one connected rule: examine plausible fix candidates before committing to the first implementation when material design uncertainty exists, and **re-enter the same adequacy reasoning on a concrete counterexample at any stage**, without waiting for a failed patch or multiple correction epochs. The challenged issue/spec assumptions, user/product contract, root cause, required scope or architectural owner may be revisited to the extent evidence demands; the prior candidate set never limits the search. Technical widening necessary to preserve the authorized result follows the existing right-level boundary. Product-authority changes and explicit user exclusions are not silently waived.

This is conditional, not a new gate for every fix. A settled, adequate fix proceeds normally. The root still owns authority/source classification, `change-contract` owns local/right-level implementation and specialist escalation, and the review/tester roles retain their independent evidence duties. The new orchestrator text unifies decision timing and scope rather than duplicating those contracts.

No new ST tests/scenarios, roles, permissions, or skill changes. Existing gate assertions for that paragraph were updated. Structural release gates do not establish behavior on Flash models.
