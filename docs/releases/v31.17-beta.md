# v31.17 beta — Proportional implementation evidence budgets

## Problem

A code change can accumulate thousands of test lines and long explanatory comments even when core implementation is much smaller. Minimalism alone is not a measurable intervention trigger. Fixed test-line ceilings unfairly constrain larger changes, while coverage percentage says nothing about duplicative test volume.

## Narrow change

The existing `skills/change-contract/SKILL.md` now specifies proportional **volume** thresholds for new, non-generated test code: `T <= max(250, ceil(1.5 * P))`, where `T` is new/rewritten test NCLOC and `P` is changed production NCLOC (per-file larger of substantive additions/removals). This is not test coverage. Small changes get a 250-line allowance; exceptional test-only/deletion-led cases are judged on independent coverage, not an artificial denominator.

For non-generated production edits, target comment density at or below 15%; above 20% requires justification and authorization if excess remains necessary. Documents, legally required notices, interface contracts and difficult invariants are not to be erased to meet a ratio. No automatic code-coverage requirement or project dependency is introduced.

At or before a budget breach, consolidate duplicated fixtures, test cases and repetitive commentary, then send the remaining excess and risk/coverage case to the workflow owner for **user authorization**. Never hide missing tests, pad implementation, split changes unnaturally, or confuse a reviewer hypothesis with a necessary added test. These thresholds are decision triggers, not hard CI failures or mandatory test quantities.

## Preservation

Only the canonical engineering skill changes semantically. Existing stage routing, reviewer independence, architecture choice, agent permissions, tools, and installer behavior are unchanged. A narrow static policy guard protects budget wording; semantic review against v31.16 and fresh release gates remain mandatory.
