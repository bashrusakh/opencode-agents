# v28.34 release notes

v28.34 is a focused right-level-fix release on top of the real v28.33 baseline. It keeps v28.33 routing, role boundaries, verification cadence, current-upstream freshness, repository state identity, PR base-drift handling, failed-fix reset, user-decision batching, output rules, and PR lifecycle unchanged.

## Outcome-owned fix boundary

**Before:** the pack required root-cause analysis, similar-caller inspection, and right-level/shared fixes, but an agent could still choose the nearest reusable component or per-partition mechanism even when that boundary could not guarantee the user's end-to-end outcome. The v28.30 failed-fix reset could recover after the same material failure persisted, but it did not explicitly reject an incapable fix boundary before implementation.

**Now:** fix selection begins with the end-to-end acceptance condition for the requested outcome. Before coding, the workflow identifies the smallest ownership boundary capable of guaranteeing that condition and checks the proposed fix against the materially relevant paths, states, callers, partitions/instances, and lifecycle transitions. A local or per-partition guarantee is not treated as a system-level guarantee unless its composition/aggregate behavior is established.

If the proposed boundary cannot guarantee the acceptance condition, the workflow moves the fix level outward or escalates before implementation instead of accumulating locally valid but globally insufficient patches.

## Relationship to existing safeguards

The rules are complementary rather than duplicate:

- v28.34 is the **pre-implementation boundary check**: can this fix level guarantee the requested outcome?
- v28.30 remains the **post-mutation reset**: if the same material failure persists or evidence contradicts the root-cause hypothesis, lower confidence and reassess before another similar patch.
- v28.31-v28.33 remain the **state-evidence safeguards**: current-target freshness, end-to-end repository state identity, and `Base SHA + Candidate HEAD` evidence binding are preserved.

Together they reduce initial wrong-level fixes, repeated patch-by-inertia loops, and fixes/reviews performed against the wrong repository state.

## Role alignment

The canonical rule lives in root `AGENTS.md` under right-level fixes. Short role-specific enforcement is aligned in:

- `agents/code-orchestrator.md` before mutation dispatch;
- `agents/plan.md` when selecting ownership/fix level;
- `agents/debugger.md` before applying a bugfix;
- `agents/build.md` before focused edits to existing/shared behavior;
- `agents/reviewer.md` when judging whether a patch actually satisfies its outcome-level contract.

No new agent, skill, mandatory stage, model binding, permission, approval gate, OCR policy, verification cadence, or PR lifecycle change is introduced.
